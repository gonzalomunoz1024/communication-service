## 2. Architecture

### 2.1 Frontend → backend

- Single-page app, two tabs. `createCommunicationClient(baseUrl, {clientId})` (`api.ts:219-266`) wraps four calls:
  `POST /v1/communications` (publish), `GET /v1/feed?tenantId&service&type&severity&page=0&size=100` (feed), `POST /v1/communications/{id}/retire` (resolve), `GET /v1/feed/stream?…&clientId=` (SSE via `EventSource`).
  The UI never calls `/v1/communications/{id}`, `PUT`, `/publish`, `/v1/admin/**` or `/v1/health/**`.
- Identity: `X-Client-Id: communication-frontend` on every fetch (`api.ts:228-232`); the stream passes `?clientId=` because `EventSource` cannot set headers (`api.ts:252`, accepted by `ClientIdWebFilter.java:82-89`).
- No auth of any kind beyond that header; tenant and publisher are plain request fields typed by the user.
- CORS: the backend has **no CORS configuration**. In development the Vite proxy makes the API same-origin (`vite.config.ts:17-24`). A static build must be served behind the same host as the API; `VITE_API_BASE` pointing at another origin would be blocked by browsers (open question Q2).
- Live model: one `GET /v1/feed` page (≤100 items) then SSE frames applied by `applyEvent` (`feed-state.ts:328-337`); the UI recomputes effective status from `startsAt`/`expiresAt` because SSE payloads carry the *stored* status (`feed-state.ts:293-298`). Browser reconnects send `Last-Event-ID`; the server replays the gap (`FeedUseCase.java:76-85`).
- Error surfacing: `ApiError(status, message)` with the service's `{"error"}` text (`api.ts:157-165,196-204`).

### 2.2 Backend internals that verifiers must know

- Vertical slices under `com.atlas.communication`: `publishing` (commands + sweeper + ticket policy), `feed` (queries + SSE), `admin`, `health` (monitors, probes, reports, rollup, scheduler), `common` (aggregate, Mongo adapters, event log), `config` (client-id filter, error handler, OpenAPI, clock), `servicenow` (properties only, nothing calls ServiceNow).
- Scheduled jobs (`@EnableScheduling`): `StatusSweepUseCase.sweepScheduled` every 30 s; `HealthSweepUseCase.sweepScheduled` every 5 s (initial delay 5 s); event-log tail every 500 ms (`@PostConstruct` subscription, not `@Scheduled`).
- Multi-instance safety: optimistic `@Version` on communications and monitors; notice "claim" saves the monitor before creating the communication (`HealthObservationUseCase.java:75-82`); sweeper conflicts are skipped.
- Event fan-out is a Mongo poll of `communication_events` (no change streams, so a standalone `mongod` is enough).
- Health evaluation is single-store (claim + communication = two writes with compensation), documented as a v1 constraint in the root README.

### 2.3 Sidecar ↔ app container ↔ backend

- **Sidecar → app**: containers of a pod share one network namespace, so the sidecar lists listening TCP ports from its own `/proc/net/tcp` and `/proc/net/tcp6` (`discover/ports.go:24-50`) and probes `127.0.0.1` / `::1` (`CS_HOST`). No shared volume, no Unix socket, no Kubernetes API, no RBAC, no secrets. Probe ladder: `/actuator/health` on any port → `/health,/healthz,/readyz,/ready,/livez,/q/health` → `/` → TCP connect (`probe.go:351-399`); `http` then `https` fallback on a TLS hint; localhost TLS unverified (`probe.go:198-216`).
- **Sidecar → backend**: `POST <CS_ENDPOINT>/v1/health/reports` with `X-Client-Id`, `User-Agent: health-sidecar/<version>` (`report/client.go:487-514`). Sent on status/component-signature change or every `CS_HEARTBEAT`; exponential backoff 1 s→60 s (+20 % jitter) on failure keeping only the latest report; 4xx except 408/409/429 is permanent (`agent.go:251-292`). On SIGTERM one last report with `instance.leaving: true` (`agent.go:294-311`). HTTP(S)_PROXY from the environment is honoured for reports (`report/client.go:471`), never for localhost probes.
- **Backend side of the contract**: `HealthReportCommand` (`HealthReportCommand.java:141-155`) + `ReportInstance` (`ReportInstance.java:195-203`). Reports with `instance` are stored per pod (`health_instances`, TTL 1 day) and rolled up (`HealthRollup.java:279-314`) before the monitor's debounce; auto-registered instance monitors get `staleAfterSeconds = 90` (`HealthMonitorUseCase.java:138-143`).
- **Deployment of the sidecar** (the only manifests in the repo):
  - Kustomize component `sidecar/deploy/kustomize/component` (`kind: Component`, JSON-6902 patch targeting `kind: (Deployment|StatefulSet)`), appending container `health-sidecar` (`add-sidecar.yaml`); native-sidecar variant `add-native-sidecar.yaml` (initContainer with `restartPolicy: Always`) to be swapped in by hand; example overlay with a `configMapGenerator` (`cs-health-sidecar`: `CS_ENDPOINT`, `CS_TENANT`, `CS_CLUSTER`, `disableNameSuffixHash`).
  - Helm **library** chart `cs-health-sidecar` 1.0.0 with `cs-health-sidecar.container` / `.initContainer` templates and `csHealthSidecar.*` values (`endpoint`/`tenant` required).
  - Plain YAML `deploy/manual/deployment.yaml` (ConfigMap + container block).
  - In all three: image `registry.example.com/platform/health-sidecar:1.0.0`, `envFrom` the ConfigMap (Kustomize/manual) or literal env (Helm), Downward API `POD_NAME`/`POD_NAMESPACE`/`NODE_NAME`, `CS_SERVICE` and `CS_VERSION` from `app.kubernetes.io/name|version` labels, port `cs-status` 9465, liveness `GET /healthz` every 30 s, requests `10m/16Mi`, limits `50m/32Mi`, `securityContext: {allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, runAsNonRoot: true, capabilities.drop: [ALL], seccompProfile: RuntimeDefault}`, no `runAsUser` (arbitrary UID), **no readiness or startup probe, no preStop, no terminationGracePeriodSeconds**.
  - Nothing deploys the **backend** or the **frontend**: no Deployment/DeploymentConfig, Service, Route, Ingress, ConfigMap, Secret, SCC, NetworkPolicy, Dockerfile or Helm chart exists for them. No ServiceAccount or SCC binding is needed by the sidecar (restricted-v2 is the OpenShift default).
  - The planned mutating admission webhook (annotation-triggered injection) and projected-token auth do **not** exist in the repo.

### 2.4 What does not exist (so verifiers do not look for it)

- No authentication/authorization, no CORS config, no rate limiting, no Actuator (the backend has no `/actuator/health`; `GET /actuator/**` is 404).
- No backend/frontend containerisation or manifests; no docker-compose; no CI.
- No admin or health-monitor screens in the UI; no paging in the UI feed (first 100 items only).
- No ServiceNow API calls (ticket is a reference + link only).
- No webhook injector; no sidecar metrics endpoint (only `/healthz` and `/status`).
