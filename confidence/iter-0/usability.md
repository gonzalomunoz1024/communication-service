## 5. Not exercised here, and why

- No OpenShift or kind cluster (nested containers do not run in this sandbox): the sidecar was attached as Docker containers and the manifests were rendered (`kustomize build`, `helm template`), never applied; nothing about the OpenShift console or `oc` ergonomics was reviewed.
- The ticket link (`ticket.url`) requires `communication.servicenow.instance-url`, which the shared backend does not set; the chip was reviewed as text only.
- A screen reader was not run; the accessibility review used the accessibility tree (`ariaSnapshot`), axe-core 4.10 (WCAG 2.x A/AA) and keyboard traversal in Chromium.
- Phone checks used Chromium device emulation (390×844, touch), not a device.
- The browser-side `Last-Event-ID` resume (F-20 through the UI) could not be judged on its own because the server answers 500 (UX-20); a 500 is a non-200 answer, so the browser will stop retrying exactly as observed for the 502 in UX-6 (b), which means that once F-20 is reachable (a browser reconnecting with an id after a real drop) the stream dies the same way until UX-6 is fixed too.

## 6. Positive observations (so the scores are read in proportion)

UI: consistent design in both themes; live propagation < 1 s both ways; skeletons and a spinner the moment a load starts; every validation message sits under its field and is announced; the 409 keeps the input and is in view; the resolve flow states the consequence before acting; tab order is logical with visible focus everywhere; Enter submits; hash routing keeps the tab across reloads; no horizontal overflow on a phone; no JavaScript errors in the console during any walk (only the browser's own log line for a 409 response).
